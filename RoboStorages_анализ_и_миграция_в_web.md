# RoboStorages 10.31 — анализ приложения и план переноса в web

> Анализ выполнен путём разбора .NET-сборок из архива (парсинг CLI-метаданных ECMA-335: типы, namespace'ы, методы, плюс извлечение строковых констант — SQL-запросов, конфигурации). Полной обратной трансляции IL→C# не делал (среда без интернета, без ilspy/dotnet), но для планирования архитектуры этого достаточно: видна вся карта классов, методов и прямых SQL-запросов, которая и определяет бизнес-логику.

## 1. Что это за приложение

**RoboStorages** — desktop WMS (система управления складом) на **.NET Framework 4.8.1 / WinForms**, версия 10.31. Судя по терминологии (Честный Знак/HonestSign, GTD/ГТД, "Stutzen", позиции/поставки/отгрузки) — склад товаров с обязательной маркировкой, работающий в связке с торговой/учётной системой **"Stutzen"** (stutzen.ru) и, возможно, автоматизированным ботом уведомлений.

### Технологический стек
| Слой | Технология |
|---|---|
| UI | WinForms (+ `AdvancedDataGridView`, `AxInterop.WMPLib` — ActiveX плеер/видео с IP-камеры) |
| Доступ к данным | **Dapper** + сырой SQL (T-SQL, MS SQL Server) |
| Вторая БД | **MySQL** (`MySql.Data`) — интеграция с учётной системой Stutzen |
| Экспорт/импорт | `ClosedXML`, `DocumentFormat.OpenXml`, Excel Interop (через `IVAFRAMEWORK.dll`) |
| Штрихкоды/этикетки | `Zen.Barcode.Core`, `QRCoder`, кастомный `PrintStickerService` |
| Интеграции | `Tradesoft.dll` (клиент к учётной системе), `APIStutzen.dll` (Autobot — похоже на бота уведомлений/мессенджер), `IVAFRAMEWORK.dll` (общий framework: Excel, письма-заказы, документы) |
| Локализация | ru, fr, + кастомный ресурс-пак (замена под "lkt-US") |
| Прочее | IP-камера склада (WMPLib), сканер штрихкодов, физическая печать этикеток/накладных |

## 2. Архитектура (как есть)

Классический **desktop 2-tier**: UI-формы напрямую дёргают статические сервис-классы, которые формируют и выполняют SQL. Настоящего доменного/сервисного слоя, DTO или разделения ответственности нет — это **God classes**:

- **`RoboStorages.Services.LocalDb`** — ~130 методов, вся работа с локальной MS SQL Server базой (`mssqllocaldb`): позиции, задания склада (StockTask), статусы, честные знаки/маркировка, пользователи, права, события, стикеры, замены, недостачи/пересорт.
- **`RoboStorages.Services.StutzenDb`** — ~60 методов, чтение/запись во внешнюю MySQL-базу учётной системы Stutzen: позиции поставщиков, клиенты, цены, задачи склада на стороне ERP.
- **`RoboStorages.Services.API`** — тонкий HTTP-клиент (проверка версии и т.п.)
- **`RoboStorages.Services.PrintStickerService`** — рендер и печать этикеток (Code128, размеры/масштаб).

Формы (`RoboStorages`, `RoboStorages.MenuForms`, `RoboStorages.UI`, `RoboStorages.UIControls.*`) — это, по сути, "контроллеры + вьюхи" в одном файле: ~65 форм/юзер-контролов, среди них ключевые бизнес-сценарии:

- **Приёмка/склад:** `FormStock`, `FormStockInput`, `FormStockInputShip`, `AllPositionsStorage(-Done/-Old)`, `UCStorageAvtoTask`
- **Оператор:** `OperatorInputDay`, `OperatorSettings`, `UCLogWork`, `UCPositions1`, `UCProviderPrice`
- **Отгрузки:** `Shipments`, `ShipmentsSettings`, `UCShipment`, `UCShipped`
- **Маркировка/этикетки:** `Markirovat`, `FormPrintSticker`, `FormStockInputMark(Logs)`, `FormHonestSignInfo`
- **Управление:** `FormManager`, `FormManagerSettings`, `FormUsers`, `EditUser`, `PositionEdit`, `FormStatusesSettings`
- **Поставщики/клиенты:** `SelectProvider(2)`, `FGrp_provider`, `UCProviderReconActs`, `Stocks`
- **Аналитика/журналы:** `StockStats`, `EventsLog`, `Form1CLogs`, `PositionsLog`, `DetailsInfo`

Доменная модель (`RoboStorages.Models.*`, 55+ классов) — по сути анемичные DTO, отражающие таблицы БД: `Position`, `PositionStorage`, `Stock`, `StockTask`, `Provider`, `Customer`, `User`, `HonestSign`, `PrintSticker`, `PositionsLog`, `AutoStatusPosition`, `TaskArrival` и т.д.

### Проблемы текущей архитектуры (важно для миграции)
1. **Бизнес-логика размазана по SQL-строкам** внутри `LocalDb`/`StutzenDb` — нет единого источника правды по бизнес-правилам (расчёт статусов, авто-статусы, недостачи/пересорт и т.д. реализованы built-in в SQL и в code-behind форм).
2. **Прямая связь UI ↔ SQL**, нет API-слоя — типичная монолитная desktop-модель, которую нельзя просто "поднять" в браузере.
3. **Две независимые БД** (MS SQL + MySQL) с cross-database запросами — при переносе в web нужно явно спроектировать интеграционный слой вместо ad-hoc SQL join'ов.
4. **Завязка на десктопное окружение**: ActiveX (Windows Media Player) для IP-камеры, локальные принтеры этикеток/накладных, локальный сканер штрихкодов через клавиатурный ввод (`KeyboardLayoutHelper`, `AutoCompleteTextBox`), Excel Interop (COM, требует установленный Office).
5. **Дублирующиеся/тестовые методы** (`CreateStockTaskTest`, `CreateStockTaskTest2/3`, `GetPositions1_delete`, `GetUserEvents_delete`) — признак накопленного технического долга, стоит подчистить при миграции, а не тащить 1:1.

## 3. Целевая архитектура для web

### Общая схема
```
┌────────────────────────────┐
│  Frontend (SPA, React/Vue)  │  ← работает в браузере на складе/у оператора
└───────────────┬────────────┘
                │ REST/GraphQL + WebSocket (live-статусы, сканер)
┌───────────────┴────────────┐
│      Backend API (BFF)      │  ASP.NET Core / Node.js
│  ── Auth & права доступа    │
│  ── Domain services         │  ← сюда переносится логика из LocalDb/StutzenDb
│  ── Интеграционный слой     │  ← клиент к Stutzen (взамен Tradesoft/APIStutzen)
│  ── Печать/этикетки (PDF)   │  ← вместо GDI+ рендера — HTML/PDF или ZPL на принтер
└───────────────┬────────────┘
        ┌────────┴────────┐
        │   PostgreSQL/MSSQL │ (основная БД склада)
        └────────┬────────┘
                 │ sync/интеграция
        ┌────────┴────────┐
        │  Stutzen (MySQL) │ (внешняя система, как была)
        └──────────────────┘
```

### Backend
- **API-слой**: ASP.NET Core Web API — самый дешёвый перенос, т.к. можно частично переиспользовать C#-логику из `LocalDb`/`StutzenDb`/`Models`, просто вынеся её из code-behind в контроллеры/сервисы с DI. Dapper остаётся жизнеспособным выбором и на бэкенде.
- **Слои**: `Controllers` → `Application/Services` (бывшие методы `LocalDb`) → `Repositories` (SQL) → `Domain models`. Отдельно — `IntegrationServices` для Stutzen/HonestSign/бот-уведомлений.
- **Аутентификация**: сейчас — своя таблица `_users` с логином и SHA-256-хэшем пароля. Права хранятся тут же как **строковые списки-whitelist'ы** (`SetLoginsLeft`, `SetProviders`, `SetStocksRight` — см. раздел 9), а не в нормализованной модели ролей/прав. В вебе — JWT/сессии + нормальная таблица `user_permissions` (пользователь ↔ склад, пользователь ↔ поставщик), это даст и производительность, и возможность аудита.
- **Реалтайм**: сканирование штрихкодов, статусы заданий склада, обновление количества на полке — кандидаты на **SignalR/WebSocket**, чтобы несколько операторов видели изменения без ручного рефреша (в desktop-версии это делалось таймером `UpdatePeriod`/`AutoUpdateTasks`).

### Frontend
- SPA (React или Vue) + адаптивная вёрстка: часть экранов (оператор с ТСД/сканером) должна работать на планшете/смартфоне в браузере — то, что desktop не мог.
- Штрихкод-сканер: большинство промышленных сканеров эмулируют клавиатуру — это переносится в web почти без изменений (просто слушать `keydown` в фокусированном поле, как сейчас делает `AutoCompleteTextBox`/`KeyboardLayoutHelper`).
- Таблицы (`AdvancedDataGridView`) → любой grid-компонент (AG Grid / TanStack Table) с server-side пагинацией — сейчас похоже что многие Get-методы тянут большие выборки целиком, для web это нужно пересмотреть (пагинация, фильтры на бэкенде).

### То, что требует отдельного решения (не переносится "как есть")
| Desktop-фича | Web-альтернатива |
|---|---|
| IP-камера через WMPLib/ActiveX | HTML5 `<video>` + MJPEG/HLS-прокси на бэкенде, либо WebRTC к камере |
| Печать этикеток (GDI+, `PrintStickerService`) | Генерация PDF/ZPL на бэкенде + печать через локальный принт-агент (браузер сам печатать на термопринтер без диалога не умеет) — нужен небольшой локальный сервис-мост (или PWA + WebUSB/WebSerial для ZPL-принтеров) |
| Excel Interop (COM, требует Office) | `ClosedXML`/`OpenXML` на бэкенде — их и так уже используют, просто убрать зависимость от Interop |
| Локальные настройки принтера/сканера в `.config` | Настройки склада/рабочего места хранить в БД, привязанные к пользователю/АРМ |

## 4. Внешние интеграции, которые нужно сохранить
1. **Stutzen (учётная система, MySQL, stutzen.ru)** — сейчас доступ напрямую по SQL из клиента. Для web это нужно закрыть на бэкенде отдельным интеграционным сервисом (никогда не открывать MySQL наружу из браузера).
2. **Tradesoft.dll / APIStutzen.dll (Autobot)** — похоже на API/бот уведомлений; нужно уточнить протокол (внутри всего пара классов — `Trade`, `Autobot`/`AutobotMessage`/`AutobotResponse`), скорее всего HTTP + JSON, переносится в backend-интеграцию почти напрямую.
3. **Честный Знак (маркировка)** — таблицы `PositionsStorageHonestSignCodes`, методы `SetScannedPositionsStorageHonestSignCode*` — это уже критичная для законности продаж интеграция, нужно вынести в отдельный сервис с логированием (`PositionsStorageHonestSignCodesLog` уже на это намекает).
4. **ГТД/GTND** (`RoboStorages.Models.GTND`) — таможенные декларации, `GTDURLActivate` в конфиге ссылается на `stutzen.ru/admin/common_import.html` — веб-форма импорта на стороне Stutzen, которую сейчас дёргают URL-ом; тоже кандидат на нормальный API-вызов.

## 5. Рекомендуемый план миграции (поэтапно, strangler fig)

1. **Инвентаризация бизнес-правил.** Вытащить в явные спецификации логику, зашитую в SQL/code-behind (авто-статусы, расчёт недостачи/пересорта, правила прав `TaskRight`). Без этого шага перенос превратится в перенос багов.
2. **Спроектировать единую БД-стратегию**: либо остаться на двух БД с интеграционным слоем (быстрее), либо консолидировать в одну (дороже, но чище). Учитывая что Stutzen — внешняя система не под вашим контролем, скорее всего логичнее оставить её отдельно и синхронизировать через API/очередь.
3. **Backend API** — перенести `LocalDb`/`StutzenDb` методы в сервисы с DI, без UI-зависимостей. На этом этапе desktop-клиент можно оставить работать через тот же API (thin client) — так снижается риск "большого взрыва".
4. **Frontend по модулям**, в порядке бизнес-приоритета, например: Приёмка склада → Отгрузки → Маркировка/этикетки → Управление/справочники → Аналитика.
5. **Печать и сканирование** — решить отдельно и рано, т.к. это самый нетривиальный "физический" кусок (термопринтеры, ТСД, камера).
6. **Параллельный запуск** двух систем на складе, сверка данных, затем отключение desktop-версии по модулям.

## 6. Что стоит уточнить у бизнеса/пользователей перед стартом
- Точный список ролей и прав (сейчас разбросан по `TaskRight`, `GetSetLoginsLeftAsync`, `GetStockRightAsync`, `GetSetProvidersLeftAsync`).
- Модель принтеров этикеток/накладных (модели, протокол — ZPL/EPL/GDI-драйвер?) — от этого зависит архитектура печати в вебе.
- Требования к офлайн-работе на складе (нестабильный Wi-Fi — актуально для WMS): в desktop-версии всё было локально, в web понадобится стратегия деградации (PWA + offline-очередь сканов?).
- Формат общения с IP-камерой (модель/протокол).
- Протокол `Tradesoft`/`Autobot` — что именно это за интеграция (нужен доступ к их API/докам, в бинарнике только имена классов, не тела методов).

## 7. Находки по исходному коду (ilspy-декомпиляция ключевых классов)

После разбора реального кода (`LocalDb.cs`, `FormLogin.cs`, `Program.cs`, `Trade.cs`, `API.cs`, `Autobot.cs`, `TaskRight.cs`, `_user.cs`) картина уточнилась и добавились находки, часть из которых критична и не зависит от сроков web-миграции.

### 🔴 Критично — требует действий уже сейчас, независимо от переноса в web
1. **Учётные данные в открытом виде в коде.** Пароль от MS SQL Server (поле `_connection` в `LocalDb.cs`) и от MySQL (в `Trade.cs`), а также `ApiKey` к `api.stutzen.ru`/`catalog.stutzen.ru` — захардкожены в исходниках как plaintext-строки. Раз это увидел анализ по декомпилированному коду — значит, потенциально доступно любому, у кого был установщик приложения. **Рекомендация: ротировать все эти секреты уже сейчас**, до начала миграции, а не откладывать до web-версии.
2. **Пароли пользователей хранятся как SHA-256 с одной фиксированной солью на всех** (`FormLogin.cs`: `sha256(password + "Stutzen0202")`), соль зашита в клиенте. Для web нужен bcrypt/argon2 со случайной солью на пользователя. Существующие хэши можно смигрировать "лениво": при следующем успешном логине проверять по старой схеме и тут же перехешировать в новую, не заставляя всех сбрасывать пароли разом.
3. **Путаница из-за одинаковых имён у двух разных БД.** `RoboStorages.Services.LocalDb`, вопреки названию, работает не с локальной, а с **удалённым MS SQL Server** (`Data Source=90.188.26.75`, `Initial Catalog=ar_stutzen`) — это отличается от того, что написано в `RoboStorages.exe.config` (там задан `mssqllocaldb` для EntityFramework, но реально в коде используется прямой `SqlConnection` на удалённый сервер, EF, судя по всему, не используется вовсе). При этом `StutzenDb`/`Trade.cs` ходят в **отдельный MySQL** (`87.228.10.222`), где тоже есть база/схема с именем `ar_stutzen`, но это другая система (сайт/учётка Stutzen). В коде постоянно встречается `[ar_stutzen].[dbo].[...]` — важно не перепутать, о какой из двух баз идёт речь в каждом конкретном месте. **Нужно уточнить у вас/у Stutzen**, как именно синхронизируются эти две базы (или это два независимых источника данных, которые WMS просто параллельно читает/пишет) — от этого сильно зависит архитектура интеграционного слоя.

### 🟡 Главный архитектурный вызов для web: глобальное mutable-состояние
Это оказалось важнее, чем масштаб "God classes". Приложение хранит текущий контекст работы — пользователя, "текущую" сканируемую позицию, выбранное задание, права — в **статических классах**: `AppData` (Login, StockId, права, настройки печати, честный знак...), `AppPosition` (данные текущей позиции), `SelectedTask`, `TaskRight` (`RoboStorages.Models.Manager.TaskRight`) — у всех свойства объявлены как `static`.

Пример: метод `LocalDb.SetScannedPositionsStorageHonestSignCode(id, originalCode)` берёт `AppPosition.Articul`, `AppPosition.Manufacturer`, `AppPosition.Name`, `AppPosition.RefClient` **не из своих параметров**, а из глобального статического поля, которое где-то раньше выставил UI-код. В desktop-приложении (один процесс = один пользователь) это безопасно. **На web-бэкенде так работать не может**: один процесс сервера параллельно обслуживает много пользователей — статические поля станут общими для всех запросов, и это гарантированно приведёт к гонкам данных и утечкам между сессиями разных операторов склада.

→ При переносе логики из `LocalDb` в сервисы бэкенда весь неявный контекст (`AppData.*`, `AppPosition.*`, `SelectedTask.*`, `TaskRight.*`) нужно **сделать явными параметрами методов/полями DTO запроса**, а не переносить статику 1:1. Это самая трудоёмкая, но обязательная часть рефакторинга — по сути, весь `LocalDb.cs` (3456 строк) нужно построчно проверить на скрытые обращения к этим глобальным классам.

### 🟢 Бизнес-правила оказались проще, чем можно было ожидать
- `PositionStorageSetQuantityMarriage` / `...Shortage2` / `...ReGrading` — простые прямые `UPDATE` одного поля таблицы `PositionsStorage`, без скрытой логики валидации или пересчёта на уровне `LocalDb`. Если такие правила есть, они реализованы в UI (проверить на формах при разборе), а не в слое доступа к данным.
- `GetEnableAutoStatusPositionsIn/Out` — обычный булевый флаг из таблицы `_users`, читается один раз при логине в `Program.cs` и кладётся в `AppData`, а не пересчитывается динамически.
- **`StockTask` — простой конечный автомат статусов**: `1` (создано) → `2` "в работе" (`StockTaskToWork_Warehouse`, ставит `StartTime`) → `4` "завершено" (`StockTaskComplete_Warehouse`, ставит `EndTime`). При этом в `StockTaskUpdateStatus` есть отдельная ветка `case 3`, которая тоже проставляет `EndTime`, но нигде из просмотренного кода статус `3` явно не выставляется тем же методом, что и `StockTaskComplete_Warehouse` (который жёстко использует `4`). **Стоит уточнить у бизнеса/протестировать вживую**, что означает статус `3` — вероятно, промежуточное состояние вроде "готово, но не подтверждено", отличное от финального "завершено".
- Обнаружено дублирование: три почти идентичных метода — `SetScannedPositionsStorageHonestSignCode`, `...Async`, `...Sync` — делают одно и то же (транзакционно обновляют `PositionsStorageHonestSignCodes` и пишут в `PositionsStorageHonestSignCodesLogs`). При переносе в web достаточно оставить один асинхронный вариант.
- **Интеграция со Stutzen (`Trade.cs`) — это не REST API, а эмуляция браузерных POST-запросов на HTML-админку** `www.stutzen.ru/admin/...` (Basic Auth + form-urlencoded поля формы, есть даже захардкоженный сериализованный PHP-параметр `id-translate=YTozOntzOjk6InRhYmxlbmFtZSI7...`). Это самый хрупкий кусок системы: любое изменение вёрстки/полей в админке Stutzen может сломать интеграцию без предупреждения. Для web-версии стоит явно спросить у Stutzen, есть ли у них нормальный программный API, или это единственный доступный путь взаимодействия — это сильно повлияет на архитектуру интеграционного слоя.
- `APIStutzen.Autobot.SentStatus` и `RoboStorages.Services.API.GetOne/GetWorkVersionAsync` — это уже нормальные JSON REST-вызовы (`https://www.api.stutzen.ru/Autobot/SentStatus`, `https://www.catalog.stutzen.ru/api1c/HonestSign/getone`, `https://wms.stutzen.ru/api/Global/GetWorkVersion`) с авторизацией по заголовку `ApiKey`. Переносятся в backend-интеграцию почти без изменений.
- `Program.cs` подтверждает: `SelectedTask.RunForm` ("Stock" / "Manager" / "AllPositionsStorage" / "AllPositionsStorageOld") — это по сути ручной роутинг между режимами приложения, выбираемый в `FormLoginMenu` после логина. В web это прямо ложится на маршруты SPA/разные страницы личного кабинета по ролям.
- Обнаружен побочный эффект в `Program.cs`: при каждом запуске приложение делает запрос к внешнему сервису `https://whatsmy.fyi/ip`, чтобы определить публичный IP и записать его в лог пользователя (`RecordUserLog`). Мелочь, но при переносе в web эта информация и так будет доступна на бэкенде из заголовков запроса — внешний сервис не понадобится.

## 9. Находки по `FormLogin.cs`, `FormLoginMenu.cs`, `TaskRight.cs`, `PrintStickerService.cs` и правам доступа

### Меню — не набор модулей, а набор предустановленных фильтров одного экрана
Разбор `FormLoginMenu.cs` показал: кнопки вида "Управление отгрузками (Барнаул/Новосибирск/СПб/Екатеринбург/Москва/Киров)" и "Поставщики" почти все ведут в один и тот же экран (`SelectedTask.RunForm = "AllPositionsStorage"`), различаясь только двумя параметрами — `pst_state_id` (текущий статус позиции) и `pst_state_id_new` (статус, в который её нужно перевести), например:
```
btn3 → pst_state_id=3,   pst_state_id_new=15
btn4 → pst_state_id=17,  pst_state_id_new=139
btn6 → pst_state_id=199, pst_state_id_new=198
btn7 → pst_state_id=208, pst_state_id_new=209
```
Т.е. это **один универсальный экран "список позиций в статусе X → перевести в статус Y"**, параметризованный магическими числами статусов, а не десяток разных бизнес-модулей под каждый город/сценарий. Хорошая новость для web: вместо десятка страниц нужен **один параметризуемый компонент** (таблица + массовый перевод статуса) плюс справочник статусов с человекочитаемыми названиями вместо магических чисел в коде кнопок — сейчас соответствие "число ↔ смысл статуса" нигде явно не описано и восстанавливается только по тому, какая кнопка какое число ставит.

### Ступенчатая (step-up) авторизация для чувствительных разделов
Разделы `Accountant`, `Analytics`, `Operator` запрашивают **второй пароль** поверх обычного логина: открывается диалог `LoginPass` (класс не входил в присланные файлы), и модуль запускается только если `SelectedTask.authorization == true` и `authorisationNumberForm` совпадает с ожидаемым номером формы. Похоже на общий пароль на раздел, а не на персональные права конкретного пользователя. **Для web нужно решить**: либо нормальные пер-пользовательские роли (предпочтительно), либо аналог step-up auth (PIN/пароль перед входом в раздел, актуально, например, для общих терминалов). Стоит уточнить у бизнеса реальный сценарий.

### Права доступа — не роли, а списки-whitelist'ы в текстовых полях
`GetSetLoginsLeftAsync`, `GetSetProvidersLeftAsync`, `GetStockRightAsync` читают из `[ar_stutzen].[dbo].[_users]` три строковых поля — `SetLoginsLeft`, `SetProviders`, `SetStocksRight`. Судя по названию и способу использования, это не нормализованная модель ролей, а **сериализованные в строку списки разрешённых логинов/поставщиков/складов** для данного пользователя (вероятно, через запятую). Такой подход плохо масштабируется и не даёт нормального аудита. Для web — обычная нормализованная схема (`user_id ↔ stock_id`, `user_id ↔ provider_id`, таблицы many-to-many), это также автоматически снимает проблему парсинга строк на каждый запрос прав.

### `TaskRight` — вводящее в заблуждение название, это не про права
Уточнение к более ранним разделам: класс `RoboStorages.Models.Manager.TaskRight`, несмотря на название, не имеет отношения к правам доступа — это ещё один статический класс-контекст, хранящий данные **текущей накладной/задачи менеджера** (`Id`, `DcmId`, `Provider`, `Sum`, `CommentManeger`, `CommentStock`, `Name`) с методом `Clear()`. Модель прав реализована отдельно, через `_users`/`GetStockRightAsync` (см. выше). При переносе в web `TaskRight` попадает в общую категорию "глобальное mutable-состояние" из раздела 7, а не в категорию "модель прав".

### Аппаратный fingerprint — только для аудита, не для лицензирования
`FormLogin.cs` при каждом запуске собирает через WMI `ProcessorID`, серийный номер материнской платы и объём RAM (`Win32_Processor`, `Win32_BaseBoard`, `Win32_PhysicalMemory`) и передаёт их в `LocalDb.RecordUserLog`, который просто пишет строку в таблицу `UserLog` (аудит "кто, с какого железа и IP заходил"). Прямой проверки этих данных на этапе логина не найдено — это не защита от копирования, а журналирование. Для web-версии эквивалент — писать в лог user-agent, IP и, при желании, browser fingerprint, без необходимости WMI/COM.

### Пароль сохраняется в открытом виде при "Запомнить"
При включённом чекбоксе "Запомнить" `FormLogin.cs` кладёт **пароль в открытом виде** в `Settings.Default.password` (локальный XML-конфиг пользователя Windows) — отдельно от захешированного пароля, который проверяется на сервере. Это дополнительный (третий) источник утечки пароля, если получить доступ к файлу настроек на рабочей станции. В web-версии — только HttpOnly-cookie с сессионным токеном/refresh-токеном, ни в коем случае не пароль в localStorage.

### `PrintStickerService` — приятное исключение, готов к переносу почти без изменений
В отличие от остального кода, `PrintStickerService` спроектирован корректно: не статический класс, принимает `PrintSticker settings`, `printerName`, `AppPositionPrint appPositionPrint` через конструктор (не через глобальные `AppData`/`AppPosition`), логика рендера этикетки (`Render(Graphics g)`) — чистый GDI+, координаты и размеры полей берутся из объекта-шаблона `PrintSticker` (по сути, декларативный шаблон этикетки: X/Y/размер шрифта на каждое поле — артикул, штрихкод, QR "Честный знак", комментарий и т.д.). Для web эта логика рендера почти 1:1 переносится в серверную генерацию PDF/PNG-этикетки (например, через SkiaSharp/QuestPDF на .NET-бэкенде) — единственное, что придётся заменить, это сам вызов печати (`PrintDocument`/GDI-принтер) на PDF + печать через локальный принт-агент (см. раздел 3).

### Мелкие находки (technical debt)
- В `FormLoginMenu.cs`: мёртвое условие `if (AppData.Login == "Качайкин а") { }` — пустой блок под конкретного сотрудника; `groupBox1.Enabled = true` выставляется в обеих ветках `if/else` одинаково, условие не имеет смысла; несколько пустых обработчиков кнопок (`button9_Click`, `button11_Click_1`, `button3_Click_1`).
- В `LocalDb.RecordUserLog` и похожих методах используется антипаттерн `Parameters.AddWithValue("@x", SqlDbType.Xxx).Value = ...` — `AddWithValue` в реальности не принимает `SqlDbType` вторым параметром так, как задумано (это создаёт параметр с типом object и присваивает `.Value` на возвращаемый параметр, а не использует явное указание типа как это выглядит на первый взгляд) — рабочий, но вводящий в заблуждение способ работы с параметрами; в web-версии с Dapper это естественным образом уйдёт.

## 10. Полный разбор `LocalDb.cs` (все 130 методов)

После построчного просмотра всего файла (не только приоритетных методов из раздела 9) картина дополнилась системными находками, которые касаются кода целиком, а не отдельных функций.

### 🔴 SQL-инъекция — подтверждённая уязвимость
`UpdateCommentManager(string id, string comment)` строит `WHERE`-условие конкатенацией строк:
```csharp
sqlCommand.CommandText = "UPDATE[dbo].[StockTasks] SET [Comment] = @Comment WHERE id = " + id + "; ";
```
`id` типа `string` вставляется в SQL напрямую, не через параметр — классическая SQL-инъекция, если значение хоть когда-то приходит не из полностью доверенного источника. Тот же паттерн конкатенации `id` в SQL-строку встречается и в `PositionEdit` (там `id` типа `long`, поэтому риск ниже, но паттерн тот же и его стоит исключить системно). **При переносе в web — обязательный аудит всех мест, где идентификаторы попадают в SQL-строку через `+`, а не через параметр**, вне зависимости от того, попал ли конкретный случай в выборку этого анализа.

### Три независимые, не связанные друг с другом системы статусов
Разбор `GetPositions3_Warehouse` раскрыл реальные значения `PositionsStorage.StatusPosition`:
```
1 — Необработана
2 — Частично
3 — Принята
4 — Излишек
5 — Отсутствует
```
Это **отдельная** система от статусов `StockTask.Status` (1/2/4, см. раздел 7) и от пар `pst_state_id`/`pst_state_id_new`, которыми параметризуется экран "AllPositionsStorage" из меню (раздел 9). Итого в приложении **три параллельных, независимо развивающихся статусных механизма** на разных сущностях уровня "позиция товара", "задание склада" и "фильтр экрана". При перепроектировании их стоит явно развести в модели (три разных enum/справочника), не пытаясь свести к одному понятию "статус".

### Список глобальных статических контекстов пополнился
Помимо `AppData`, `AppPosition`, `SelectedTask`, `TaskRight` (раздел 7), в `LocalDb.cs` обнаружено обращение к ещё одному статическому классу — **`Position2`** (`Position2.Articul`, `.Manuf`, `.Ref`, `.price`, `.Name` — используется внутри `Position2AddCount` без передачи как параметра) и к **`AppPositionPrint`** (используется в методах печати). Итоговый список статических контекстов, которые нужно сделать явными параметрами при переносе логики в backend-сервисы: **`AppData`, `AppPosition`, `AppPositionPrint`, `SelectedTask`, `TaskRight`, `Position2`** — шесть классов, пронизывающих весь код.

### Несистемная транзакционность
`CreateInvoice` — единственное место во всём файле, где явно используется SQL-транзакция (`BeginTransaction`/`Commit`/`Rollback`). Большинство многошаговых операций (например, `Position2AddCount`, которая последовательно выполняет три независимых `ExecuteNonQuery` — обновление количества, обновление времени, вставку в лог) транзакций не используют. При сбое посередине такой цепочки данные могут остаться в противоречивом состоянии. В web-версии транзакционность стоит закладывать системно на уровне сервисного слоя (unit-of-work), а не точечно там, где вспомнили.

### Прочее
- **`ServerDetect1()` и `ServerDetect2()`** — байт-в-байт идентичные методы (health-check соединения с БД через `SELECT TOP(1) [Id] FROM StockTasks`), дубль под разными именами — ещё один пример накопленного технического долга.
- **Ручная обработка часового пояса прямо в SQL**: `GetPositions3_Warehouse` и похожие read-методы используют `DATEADD(HOUR, @hour, [поле])`, где `@hour` берётся из глобального `AppData.lz_h`. Хрупкий паттерн, завязанный на то, что часовой пояс "текущего пользователя" выставлен где-то заранее в статике. В web разумнее хранить время в UTC и конвертировать в часовой пояс пользователя на фронтенде/в DTO при ответе API.
- **`InsertIntoPositionsLogs`** — приятное исключение на общем фоне: единственный "лог-хелпер" в файле, который **не** обращается к глобальным `AppData`/`AppPosition`, а принимает все нужные данные явными параметрами метода. Хороший образец того, как должны выглядеть остальные методы после рефакторинга под web.
- `UpdateUserPassword` пишет в Debug-лог логин и уже хэшированный пароль (`Debug.WriteLine(login + " " + password)`) — не критично (пароль хэширован), но избыточно и стоит убрать при переносе.

### Итог по `LocalDb.cs`
Скрытой сложной бизнес-логики (нетривиальных расчётов, хитрых ветвлений) в файле не обнаружено — все 130 методов представляют собой вариации CRUD-операций над ~15 таблицами, переходы между тремя независимыми статусными системами и запись в таблицы аудита. Это хорошая новость: **основная сложность миграции — не в алгоритмах, а в сквозных паттернах** (глобальное состояние, точечные SQL-инъекции, несистемная транзакционность, смешение трёх статусных моделей), которые проявляются одинаково почти в каждом методе файла. Рефакторинг под web целесообразно делать не "метод за методом", а через единые сквозные решения: один DI-контейнер вместо статики, один слой параметризованных SQL-запросов (Dapper с обязательными параметрами), единый unit-of-work для транзакций, единая модель статусов на каждую сущность.

## 11. Находки по `FormStock.cs`, `FormManager.cs`, `StutzenDb.cs`, `Markirovat.cs`, `FormHonestSignInfo.cs`, `LoginPass.cs` и глобальным контекстам

Это самый важный по содержанию раздел: именно здесь, а не в `LocalDb.cs`, обнаружилась реальная бизнес-логика приложения. Вывод раздела 10 ("скрытой сложной логики не найдено") был верен **только для `LocalDb.cs`** — вся значимая логика оказалась в code-behind форм, что для миграции даже хуже: слой доступа к данным полностью анемичен, а решения принимаются прямо в обработчиках UI-событий.

### 🔴 Третья пара захардкоженных учётных данных + фрагильная интеграция статусов
В `FormStock.PositionsSetStatus` обнаружен ещё один хардкод: логин/пароль **`"autobot"` / `"SuperMot344"`** для Basic Auth к `www.stutzen.ru`. Метод в точности повторяет паттерн из `Trade.cs` (раздел 9) — эмулирует браузерный POST на HTML-страницу админки (`admin/eshop/orders/positions_provider_list.html`), подделывает `User-Agent` под Chrome/Opera, отправляет `application/x-www-form-urlencoded` тело с полями формы (`actionType=changeState`, `newState=...`, `checkPos=...`). Это подтверждает: **у Stutzen нет нормального API для смены статуса заказа**, интеграция держится на неофициальной эмуляции конкретной HTML-формы конкретной версии их админки. Итого известных захардкоженных секретов в клиенте — **три**: пароль MS SQL, пароль MySQL, и теперь пароль `autobot`.

### Найдена реальная бизнес-логика: расчёт статуса приёмки и автосинхронизация с Stutzen
`FormStock.SavePosition` — центральный метод "принять товар по скану" — делает следующее:
1. Берёт уже принятое количество (`LocalDb.DetermineQuantityAccepted2`), прибавляет только что отсканированное (`SelectedTask.CountPlus`).
2. По соотношению принято/по накладной вычисляет внутренний статус позиции:
   - `0` принято = **1** (Необработана)
   - принято < по накладной = **2** (Частично)
   - принято == по накладной, без брака/недостачи/пересорта = **3** (Принята)
   - принято == по накладной, но **есть** брак/недостача/пересорт = **6** — это значение статуса не встречалось раньше (раздел 10 фиксировал только 1–5); фактическая шкала `PositionsStorage.StatusPosition` — **1, 2, 3, 4, 6** (5 "Отсутствует" выставляется, видимо, в другом месте, не в этом методе).
   - принято > по накладной = **4** (Излишек)
3. Если включена настройка `AppData.DoNotTakeInExcess` и получившийся статус — "Излишек", **сохранение блокируется** (склад не может принять больше, чем в накладной, если политика это запрещает).
4. Если статус — "Принята" (3) чисто, **и** у пользователя включён `AppData.EnableAutoStatusPositionsIn`, **и** задан целевой статус `AppData.InPositiononsStatusId` — запускается **fire-and-forget** асинхронная задача (без `await`, ошибки гасятся пустым `catch{}`), которая:
   - читает текущий статус позиции на стороне Stutzen (`StutzenDb.GetPositionStatus`, MySQL `ar_stutzen.positions.pst_state_id`);
   - сверяет его с **захардкоженным списком из 93 разрешённых значений статуса** (написан как 93 отдельных `if (state_id == N) { statuses.Add(pst_id); }` вместо одного `HashSet`/`IN`-условия) — это защита от смены статуса из "неправильного" состояния заказа;
   - если статус подходит — вызывает уже упомянутый `PositionsSetStatus` (HTML-эмуляция с паролем `autobot`) для смены статуса на сайте Stutzen;
   - результат логируется в `PositionsStatusLog` через `LocalDb.PositionsStatusLogInsert`.

Это резолвит открытый вопрос из раздела 9 ("`EnableAutoStatusPositionsIn` — просто флаг, где логика — неизвестно"): **логика — здесь**, в `FormStock.cs`, и она нетривиальна (расчёт статуса + guard-список + внешний вызов). Список из 93 значений при переносе в web стоит хранить не как код, а как данные — например, поле `auto_sync_eligible` в справочнике статусов `order_states` на стороне интеграционного сервиса.

### Подтверждена прямая интеграция с государственной системой маркировки "Честный Знак"
`FormManager.GetMark(string code)` обращается напрямую к официальному API ЦРПТ: **`https://cdn01.crpt.ru/api/v4/true-api/codes/check`**, передавая код авторизации из `AppData.honestSign.HonestSignKey` в заголовке `X-API-KEY`. Это отдельная, более значимая интеграция, чем локальная сверка кодов из `PositionsStorageHonestSignCodes` (раздел 9) — здесь идёт реальный запрос в государственный реестр маркировки. **Для web-версии ключ API `HonestSignKey` должен жить только на бэкенде** и ни при каких обстоятельствах не попадать в браузер — учитывая юридическую значимость системы маркировки, это не просто хорошая практика, а требование по сути дела.

### Сканирование штрихкода — сложный, специфичный протокол разбора
`FormStock.tb_KeyDown` — обработчик Enter в поле ввода скана — реализует не один, а фактически **два независимых формата** входных данных:
- со знаком `_` (например, `АРТИКУЛ_123`) — это скан этикетки самого автосклада (номер клиента/количество после `_`);
- со знаком `-` (например, `12345-2`) — это скан по ссылке поставщика + количество, сверяется с полями `RefStutzen`/`Ref Поставщика` в **уже загруженной в память таблице** (`dgvPositionsNonCompleted`), а не через запрос к БД.

Оба сценария заполняют глобальный `AppPosition` из выбранной строки грида, при необходимости открывают модальное окно ввода (`FormStockInput`), проигрывают звук (свой звук на каждого пользователя, `AppData.PickerSoundId`), печатают этикетку при необходимости и вызывают `SavePosition`. **Для web этот протокол разбора текста скана стоит перенести как есть** (это конкретный, проверенный временем формат данных с этикеток/сканеров), но сам поиск позиции должен идти через API-запрос к бэкенду, а не через перебор строк уже загруженной в браузер таблицы.

### `StutzenDb.cs`: подтверждение, что права пользователей — это одна база, не две
Несколько методов, объявленных в `StutzenDb.cs` (`GetSetLoginsLeft`, `UpdateSetStocksRight`, `GetStockRight` и др.), в реальности подключаются не к MySQL, а к **`LocalDb._connection`** (MS SQL Server). Это резолвит неопределённость из разделов 6/9: данные о правах пользователя (`SetLoginsLeft`, `SetProviders`, `SetStocksRight`) хранятся **только в одной базе** — MS SQL Server `ar_stutzen`, а не дублируются/синхронизируются между MS SQL и MySQL. При этом сама организация кода вводит в заблуждение — методы физически лежат "не в том" файле; при переносе в web стоит явно выделить модуль `UserRights`, не привязанный к тому, какая легаси-БД исторически его обслуживала.

Также в `StutzenDb.GetPositionsStatuses` обнаружен ещё один случай SQL-инъекции: `WHERE pst_pst_id IN (" + pos_ref_ids + ")"` — параметр вставлен в MySQL-запрос конкатенацией.

Отдельная good news: в MySQL есть настоящий справочник статусов заказа — **`ar_stutzen.order_states`** (`stt_id`, `stt_name`, `stt_style`, `stt_order`), а в MS SQL — аналог **`PositionsStorageStatus`**. Это значит, что для восстановления человекочитаемых названий статусов (вместо магических чисел) не нужно ничего реконструировать вручную — таблицы уже существуют и их можно выгрузить напрямую.

### Глобальные контексты — финальный список, подтверждён построчно
Полные объявления `AppData`, `AppPosition`, `SelectedTask`, `Position2` показали, что все они (кроме `Clear()`) — чистые data bag'и без логики: это хорошая новость, их перенос в web сводится к превращению в обычные DTO/Pydantic-модели и передаче явными параметрами/через сессию, без скрытых побочных эффектов при чтении/записи полей.

### Дохлый, но опасный на вид код: `FormManager.CreateStockTask`
Метод создания складского задания вручную нигде не вызывается (grep по `FormManager.cs` и `FormStock.cs` не нашёл ни одного вызова) — это мёртвый код. Важно: он вставляет позиции с **захардкоженными "тестовыми" ссылочными ID** (`RefStutzen = 8526241`, `RefProvider = 8526273`, `TradePoint = 10`, `NumberCustomer = 255457`, `PriceTotal = 574` — фиксированные числа независимо от реальных данных). Если этот метод случайно оживят или возьмут за образец при рефакторинге — это гарантированно испортит данные. **При переносе в web не использовать как референс**, реальная логика создания задания — на стороне Stutzen (заказ создаётся там, WMS только принимает его).
