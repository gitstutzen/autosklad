# RoboStorages Web

Веб-версия приложения: приёмка товара, маркировка «Честный Знак», печать этикеток. Заменяет desktop-приложение RoboStorages.

**Недавно в проекте?** Начните с `docs/README.md` — там указатель по всей документации. Если совсем с нуля — `docs/RoboStorages_архитектура_понятное_описание.md` объясняет, что делает система и из чего состоит, без технических терминов.

---

## Быстрый старт

Нужен Docker Desktop (Windows — с WSL2) и Python 3.12, если хотите запускать тесты вне контейнеров.

```bash
git clone <адрес-репозитория>
cd robostorages-web/infra
cp .env.example .env        # Windows PowerShell: copy .env.example .env
# откройте .env и заполните значения (как минимум JWT_SECRET)
docker compose up --build
```

Первая сборка занимает несколько минут. После запуска:

| Сервис | Адрес | Документация API |
|---|---|---|
| gateway | http://localhost:8000 | http://localhost:8000/docs |
| auth | http://localhost:8001 | http://localhost:8001/docs |
| warehouse | http://localhost:8002 | http://localhost:8002/docs |
| marking | http://localhost:8003 | http://localhost:8003/docs |
| print | http://localhost:8004 | http://localhost:8004/docs |
| stutzen-integration | http://localhost:8005 | http://localhost:8005/docs |

Проверка, что всё живо: откройте `/health` у любого сервиса — должно вернуться `{"status":"ok"}`.

> **Статус проекта:** каркас. Часть логики намеренно оставлена заглушками (`NotImplementedError`) — эндпоинты вернут 500/501, пока не подключена база. Это не баги, а честная граница сделанного. Полностью работают: расчёт статуса приёмки и защитные правила клиента к API Stutzen (оба покрыты тестами).

## Команды

### Docker

```bash
cd infra

docker compose up --build         # собрать и запустить всё
docker compose up -d              # запустить в фоне
docker compose down               # остановить
docker compose down -v            # остановить + удалить данные БД (полный сброс)
docker compose ps                 # что сейчас запущено
docker compose logs -f warehouse  # логи одного сервиса, в реальном времени
docker compose logs --tail=50     # последние 50 строк всех логов
docker compose restart warehouse  # перезапустить один сервис
docker compose build warehouse    # пересобрать один сервис
docker compose exec warehouse bash  # зайти внутрь контейнера
```

**Порт занят.** Если при запуске ошибка `port is already allocated` — что-то уже висит на этом порту (частый случай: локально установленный PostgreSQL). Postgres в проекте специально проброшен на `5433`, а не на стандартный `5432`. Если конфликтует что-то другое — поменяйте левое число в `ports` в `infra/docker-compose.yml`.

**Изменения в коде не подхватились.** Пересоберите образ: `docker compose up --build`. Без `--build` Docker использует старый образ.

### Тесты

```bash
cd services/warehouse
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install poetry && poetry install

pytest                             # все тесты сервиса
pytest -v                          # с именами тестов
pytest tests/test_determine_status.py::test_excess   # один конкретный тест
pytest -k "status"                 # все тесты, где в имени есть "status"
pytest -x                          # остановиться на первой ошибке
```

То же самое для любого другого сервиса — замените `warehouse` на нужный.

### Зависимости

Каждый сервис имеет свой `pyproject.toml` — зависимости не общие.

```bash
cd services/warehouse
poetry add httpx                   # добавить в обычные зависимости
poetry add --group dev pytest-cov  # добавить в dev-зависимости
poetry lock                        # пересобрать lock-файл
```

После добавления зависимости пересоберите контейнер: `docker compose build warehouse`.

### Git

```bash
git status                         # что изменено
git switch -c feat/scan-endpoint   # создать ветку и перейти в неё
git switch main                    # вернуться на main
git pull                           # забрать изменения с сервера

git add .                          # добавить все изменения
git add services/warehouse/        # добавить только один сервис
git commit -m "warehouse: добавлен поиск позиции по скану"
git push -u origin feat/scan-endpoint   # первый пуш ветки
git push                           # последующие

git log --oneline -10              # последние 10 коммитов
git diff                           # что изменилось, но не добавлено
git diff --staged                  # что добавлено, но не закоммичено
git restore <файл>                 # откатить изменения в файле
git restore --staged <файл>        # убрать файл из добавленных
```

## Правила работы команды

### Ветки и коммиты

**Не коммитить в `main` напрямую.** Всё через ветки и pull request — даже мелкие правки. Причина простая: `main` должен всегда быть в рабочем состоянии, чтобы с него можно было развернуть систему в любой момент.

Именование веток — префикс по типу задачи:
```
feat/       новая функциональность      feat/scan-position-endpoint
fix/        исправление бага            fix/status-calculation-overflow
docs/       только документация         docs/update-api-reference
refactor/   рефакторинг без новых фич   refactor/extract-db-layer
chore/      рутина (зависимости, CI)    chore/bump-fastapi
```

Коммиты — с префиксом сервиса, к которому относятся, и в повелительном наклонении:
```
warehouse: добавлен расчёт статуса при частичной приёмке
auth: исправлена проверка срока действия токена
docs: обновлён справочник API Stutzen
```

Один коммит — одно логическое изменение. Не смешивайте рефакторинг и новую функциональность в одном коммите: если потом понадобится откатить, откатится всё сразу.

### Pull request

- Название PR описывает результат, а не процесс: «Добавлен поиск позиции по отсканированному коду», а не «Правки».
- В описании — что изменилось и как это проверить. Если PR закрывает issue, добавьте `Closes #12`.
- **Нужен минимум один апрув** перед вливанием.
- CI должен быть зелёным. Красный CI не вливаем, даже «я потом починю».
- Крупный PR лучше разбить: ревьюить 800 строк никто не сможет внимательно, и баги пройдут насквозь.

### Что нельзя коммитить никогда

- **`.env` и любые файлы с реальными паролями, ключами, токенами.** В `.gitignore` они закрыты, но проверяйте `git status` перед коммитом.
- **Секреты в комментариях и документации.** Писать «пароль от базы был захардкожен в старой версии» — нормально. Писать сам пароль — нет.
- **Закомментированный код «на всякий случай».** Для этого есть история git.

Если секрет всё-таки попал в коммит — **не исправляйте это обычным коммитом**, значение останется в истории. Сообщите команде: секрет нужно считать скомпрометированным и ротировать, а историю чистить отдельно.

### Архитектурные правила

Эти три нарушать нельзя без обсуждения с командой — они держат всю конструкцию:

1. **Только `stutzen-integration` обращается к внешним системам.** Если понадобилось вызвать API Stutzen из `warehouse` — это сигнал, что что-то спроектировано не так. Добавьте эндпоинт в `stutzen-integration` и вызывайте его.
2. **Ключ «Честного Знака» живёт только в `marking`.** Никогда не передаётся в браузер и не попадает в другие сервисы. Система маркировки юридически значима.
3. **Никакого глобального изменяемого состояния.** Всё, что нужно обработчику, приходит явно — в параметрах запроса или в токене. В desktop-версии контекст лежал в статических переменных; на сервере, где параллельно работают несколько кладовщиков, это гарантированно приведёт к смешиванию данных разных людей.

### Работа с внешним API Stutzen

Отдельная осторожность — вендор прямо предупреждает о риске потери данных:

- **`DELETE` без фильтров удаляет всю сущность** (до 1000 строк). В коде клиента такой вызов запрещён программно — не обходите эту защиту.
- **Не вызывайте методы, не описанные в документации.** Если для сущности задокументирован только `GET`, поведение `POST` не определено. Список разрешённого — в `ALLOWED_METHODS` в `services/stutzen-integration/app/tradesoft_client.py`, пополняется только со сверкой по документации.

### Тесты

- Новая бизнес-логика — с тестами. Особенно расчёты статусов: это то место, где ошибка приведёт к неправильному учёту товара на складе.
- Тесты не должны ходить в сеть или в реальную базу.
- Перед пушем прогоните тесты локально — быстрее, чем ждать CI.

## Структура репозитория

```
robostorages-web/
├── services/                  # каждый сервис — независимое FastAPI-приложение
│   ├── auth/                  # логин, JWT, права (пользователь ↔ склад/поставщик)
│   ├── warehouse/             # приёмка: задания, позиции, расчёт статуса
│   ├── marking/               # «Честный Знак»: проверка кодов в гос. реестре
│   ├── print/                 # рендер этикеток в PDF/PNG
│   ├── stutzen-integration/   # ЕДИНСТВЕННАЯ точка выхода во внешние системы
│   └── gateway/               # единая точка входа для фронтенда
├── libs/common/               # общие схемы и JWT-проверка для всех сервисов
├── frontend/web-app/          # SPA
├── infra/                     # docker-compose, .env.example
├── .github/workflows/         # CI: тестирует только изменившиеся сервисы
└── docs/                      # аналитика, описание процессов, справочники
```

Внутри сервиса:
```
services/warehouse/
├── app/
│   ├── main.py       # точка входа, подключение роутеров
│   ├── routers/      # HTTP-эндпоинты (тонкие, без логики)
│   ├── service.py    # бизнес-логика — вся здесь
│   └── schemas.py    # форматы запросов и ответов
├── tests/
├── alembic/          # миграции БД
├── Dockerfile
└── pyproject.toml    # зависимости этого сервиса
```

## Ключевые архитектурные решения

- **Раздельные сервисы с первого дня.** Приёмка, маркировка, печать и интеграция меняются с разной частотой и разными людьми — их можно деплоить и откатывать независимо.
- **`stutzen-integration` — единственная точка интеграции.** Даёт один слой абстракции: можно переключиться между неофициальным `api1c` и официальным `api/v1/order-positions` без изменений в остальной системе. Плюс единое место для защитных правил вендора.
- **Синхронизация статуса — через очередь (arq/Redis).** Desktop-версия теряла ошибки синхронизации в пустом `catch{}` — сбой был невидим. Теперь задача видна, повторяется и не теряется.
- **Поиск по скану — на сервере.** Desktop-версия держала всё задание в памяти и искала там; при большом приходе это медленно.
- **MS SQL на переходный период, Postgres для нового.** Пока desktop-клиент и веб работают параллельно, `warehouse` пишет в ту же существующую базу. Остальные сервисы исторических данных не имеют и сразу на Postgres.

Подробное обоснование каждого — в `docs/RoboStorages_анализ_и_миграция_в_web.md`.
