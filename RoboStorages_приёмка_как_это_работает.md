# Как на самом деле работает приёмка товара в RoboStorages

Документ описывает процесс приёмки от начала до конца — что видит кладовщик на экране и что при этом происходит в базе данных. Составлен по коду `FormStock.cs`, `FormStockInput.cs`, `FormStockInputMark.cs`, `Markirovat.cs`, `PrintStickerService.cs`.

## Действующие лица процесса
- **Задание на склад (`StockTask`)** — приход от одного поставщика, создаётся на стороне Stutzen, попадает в RoboStorages уже сформированным.
- **Позиция (`PositionsStorage`)** — одна строка накладной внутри задания: артикул, производитель, ожидаемое количество, нужна ли маркировка "Честный Знак".
- **Кладовщик** — человек, который физически принимает коробки и сканирует/вбивает данные.

## Шаг 1. Открытие задания
Кладовщик открывает `RoboStorages → Приёмка (FormStock)`, видит список заданий и выбирает нужное. Программа показывает две таблицы:
- **не завершено** — позиции, которые ещё не приняты полностью;
- **завершено** — уже принятые.

*В базе ничего не меняется — это просто чтение текущего состояния.*

## Шаг 2. Сканирование / ввод позиции
Кладовщик сканирует штрихкод (или вводит вручную) в поле ввода и нажимает Enter. Программа ищет совпадение **в уже загруженной в память таблице** позиций этого задания (не делает новый запрос к базе на каждый скан) — по одному из двух форматов:
- **свой формат этикетки** (`АРТИКУЛ_НОМЕРКЛИЕНТА`) — если сканируется что-то, что уже промаркировано этой же программой ранее;
- **формат поставщика** (`REF-КОЛИЧЕСТВО`) — сверяется с полем "референс поставщика" у позиции.

Найденная строка заполняет рабочую карточку позиции (артикул, производитель, цена, сколько уже принято, нужна ли маркировка, есть ли предупреждение о возможном контрафакте).

*В базе ничего не меняется — это просто "открыли карточку товара".*

## Шаг 3. Диалог ввода количества
Открывается окно с данными позиции:
- артикул, производитель, цена, торговая точка назначения, комментарий;
- сколько уже принято / сколько ожидается по накладной;
- количество к добавлению (по умолчанию — то, что было отсканировано, кладовщик может поправить вручную);
- три чекбокса: **БРАК / НЕДОСТАЧА / ПЕРЕСОРТ**;
- если товар маркируемый — таблица кодов "Честного Знака" по этой позиции с отметкой, какие уже приняты.

Дальше есть **три разных сценария** в зависимости от того, что делает кладовщик:

### Сценарий А — обычная приёмка (ни один чекбокс не отмечен)
1. Если цена позиции больше 3000 ₽ — сначала показывается отдельное мигающее окно "МАРКИРОВКА — ПРОВЕРИТЬ" (это просто напоминание кладовщику присмотреться к товару, не техническая блокировка).
2. Если у позиции есть непринятые коды "Честного Знака" — **обязательно** открывается отдельное окно сканирования маркировки (Сценарий Б ниже). Пока не отсканированы все нужные коды — принять позицию нельзя.
3. Если маркировки нет или она вся уже принята — печатается этикетка (если включена настройка автопечати) и происходит фактическое сохранение:
   - в `PositionsStorage` обновляется принятое количество, статус позиции, время обработки;
   - в журнал (`PositionsLogs`) пишется отдельная запись: кто, сколько, когда принял;
   - если позиция теперь принята **полностью и без замечаний** — в фоне уходит команда на смену статуса заказа на сайте Stutzen (не дожидаясь ответа).

### Сценарий Б — сканирование маркировки "Честного Знака"
Отдельное окно со списком ожидаемых кодов этой позиции. Кладовщик сканирует код сканером:
1. Код проверяется на совпадение с одним из ожидаемых для этой позиции (сверяется первые 22 или 31 символ кода — это два разных формата кода маркировки, короткий и длинный).
2. Если совпадение найдено — этот код помечается как принятый и **сразу сохраняется в базу** (`PositionsStorageHonestSignCodes`, с логированием, кто и когда отсканировал).
3. Если код не совпадает ни с одним ожидаемым — сообщение об ошибке, код не засчитывается.
4. Как только все ожидаемые коды по позиции отсканированы — окно закрывается автоматически, и обычная приёмка (Сценарий А) продолжается: печатается этикетка, сохраняется количество.

*Важно: проверка "правильный ли это код Честного Знака вообще" (то есть настоящая сверка с государственным реестром через `cdn01.crpt.ru`) происходит **отдельно и в другом месте** программы (в `FormManager`, не здесь) — при приёмке идёт только сверка со списком уже ожидаемых кодов, загруженным для этой позиции заранее.*

### Сценарий В — брак / недостача / пересорт (отмечен один из чекбоксов)
Количество уходит не в основной счётчик "принято", а в отдельное поле той же позиции (`QuantityMarriage`, `QuantityShortage` или `QuantityReGrading`), окно сразу закрывается. Этикетка не печатается, маркировка не проверяется — этот сценарий про фиксацию проблемы с товаром, а не про полноценную приёмку.

## Шаг 4. Печать этикетки
На этикетку попадает: артикул, производитель, номер/ссылка клиента, ячейка хранения, короткое название торговой точки назначения, комментарий, код маркировки (если есть). Это ключевая деталь: **этикетка привязана не просто к товару, а к конкретному клиенту/точке назначения** — то есть уже на этапе приёмки известно, куда в итоге поедет этот товар.

## Шаг 5. Что происходит с этой информацией дальше
Отгрузка **не обрабатывается в RoboStorages** (подтверждено владельцем Stutzen) — этикетка используется физически (для сортировки на складе) и/или считывается на стороне сайта Stutzen через их собственный интерфейс/интеграцию. RoboStorages в этой части процесса не участвует.

## Сводная таблица: что меняется в базе на каждом шаге

| Шаг | Действие кладовщика | Что меняется в БД |
|---|---|---|
| Открыть задание | — | Ничего (чтение) |
| Скан позиции | — | Ничего (поиск в памяти) |
| Обычная приёмка | Ввод количества, OK | `PositionsStorage` (кол-во, статус, время), `PositionsLogs` (аудит), фоново — статус на сайте Stutzen |
| Скан маркировки | Скан кода | `PositionsStorageHonestSignCodes` (код принят), лог сканирования |
| Брак/недостача/пересорт | Чекбокс + количество | Одно из полей `PositionsStorage.QuantityMarriage/Shortage/ReGrading` |

## Что это значит для веб-версии
Процесс явно раскладывается на **два независимых API-действия**, которые можно проектировать отдельно:
1. `POST /positions/{id}/accept` — принять количество (с вариантами: чисто / брак / недостача / пересорт).
2. `POST /positions/{id}/scan-mark` — отсканировать один код маркировки.

Экран поиска позиции по скану (шаг 2) в вебе логичнее сделать **серверным поиском** (запрос к API по коду), а не загружать в браузер весь список позиций задания и искать на клиенте, как сейчас делает desktop-версия — это не только чище архитектурно, но и быстрее при большом задании (что прямо отвечает вашему требованию "быстро работать": не тащить в браузер тысячи строк ради поиска одной).
