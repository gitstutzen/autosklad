# RoboStorages → Web: скоп миграции (черновик для согласования)

Документ отвечает на вопрос "что именно переносим", отдельно от технической архитектуры (см. `RoboStorages_анализ_и_миграция_в_web.md`). Ничего в этом документе не требует чтения кода — рассчитан на обсуждение с бизнесом.

## Как читать таблицу
- ✅ **Переносим** — есть прямые доказательства в коде, что функция реально используется и критична (сложная логика, юридическая значимость, или просто это "сердце" ежедневной работы склада).
- ❌ **Не переносим** — в коде это либо не работает (пустая заготовка), либо дублирует то, что и так есть в Stutzen.
- ❓ **Нужно уточнить** — решение зависит от ответа бизнеса, у меня нет доказательств ни за, ни против по коду.

| Функция | Решение | Почему |
|---|---|---|
| Приёмка товара по сканеру | ✅ Переносим | Самая сложная и явно ежедневно используемая часть системы (расчёт статуса приёмки, брак/недостача/пересорт, печать этикеток) |
| Проверка маркировки "Честный Знак" | ✅ Переносим | Прямая интеграция с гос. реестром (`cdn01.crpt.ru`), юридически значима, не может просто исчезнуть |
| Автосинхронизация статуса заказа со Stutzen | ✅ Переносим (но переделываем механизм) | Реально работает и на неё завязана логика приёмки, но текущая реализация (эмуляция браузера, захардкоженные 93 статуса) — технический долг, не пример для копирования |
| Права пользователей / логин | ✅ Переносим (в нормальном виде) | Нужны всегда, но текущая реализация (строки-whitelist, захардкоженные PIN) переделывается с нуля, а не переносится |
| Печать этикеток | ✅ Переносим | Код рендера (`PrintStickerService`) реально используется и хорошо спроектирован |
| Отдельный модуль "Отгрузки" (`Shipments.cs`) | ❌ Не переносим | Пустая заготовка — кнопка "Обновить" ничего не делает, кроме записи в лог |
| Настройка списка разрешённых статусов (`FormStatusesSettings.cs`) | ❌ Не переносим как UI | Форма никогда не была подключена к данным; сам список (93 статуса) в вебе должен стать записью в БД/конфиге, а не экраном — экран для его редактирования можно сделать позже, если понадобится |
| Просмотр справочника складов (`Stocks.cs`) | ❌ Не переносим отдельно | Это read-only копия таблицы `stocks` из Stutzen — дешевле дёргать напрямую у Stutzen (или вообще не показывать, если это есть в их интерфейсе) |
| Внутреннее интернет-радио, настройка IP-камеры через ActiveX | ❌ Не переносим | Не относится к складской логике; камеру, если нужна, переделываем на нормальный web-стрим отдельно |
| **Отгрузка клиентам как процесс (внутри `FormStock`, не как отдельный модуль)** | ❓ Нужно уточнить | Вкладка отгрузки в `FormStock.cs` содержит реальный код (`SynchronInvoise`, работа с накладными) — это не пустышка, но неизвестно, пользуются ли ей на складе сейчас, или отгрузка полностью происходит другим способом (силами Stutzen/курьера/1С) |

## Два вопроса, которые определяют объём работы сильнее всего

### 1. Используется ли отгрузка в RoboStorages?
**Как проверить, не читая код и не спрашивая мнение "на глаз":** попросите у DBA/у того, кто администрирует MS SQL Server (адрес и реквизиты — у администратора БД; база `ar_stutzen`) выполнить простой запрос:
```sql
SELECT TOP 20 * FROM [ar_stutzen].[dbo].[PositionsShipping] ORDER BY [id] DESC;
-- и/или таблица, куда пишет SynchronInvoise / отгрузочные накладные, если она отличается
```
Если там есть свежие (за последние недели) записи — модуль используется, и его нужно переносить полноценно (это довольно много логики в `FormStock.cs`, я её ещё не разбирал так подробно, как приёмку). Если записей нет или они старые — можно смело исключать из скопа первой версии.

### 2. Есть ли шанс на нормальный API у Stutzen?
Это не блокирует старт разработки (можно начинать с сервиса `stutzen-integration`, который переносит текущую HTML-эмуляцию как есть — раздел 11 основного документа), но сильно влияет на то, сколько времени закладывать на этот сервис и насколько его стоит "прятать" за внутренним интерфейсом (чтобы потом безболезненно заменить механизм, не трогая остальные сервисы). Стоит просто задать вопрос техническому контакту на стороне Stutzen: "у вас есть REST/JSON API для чтения и смены статуса позиций заказа, help.stutzen.ru или похожее?" — если такого контакта пока нет, это тоже ответ (тогда закладываем HTML-эмуляцию как временное, но не сиюминутное решение).

## 🟢 Обновление: у Stutzen ЕСТЬ полноценный API (важнейшая находка)

Вы прислали сохранённую страницу `https://www.catalog.stutzen.ru/Admin/Api/ApiDoc2` — это документация **современного REST/JSON API** (`api1c`) на отдельном Blazor-приложении Stutzen ("Stutzen 39.08"), с авторизацией по заголовку `ApiKey` (том же механизме, что уже использует `API.cs`/`Autobot.cs` для проверок версии и Честного Знака). Извлечено и структурировано **163 эндпоинта** — полный список в `Stutzen_API_справочник.md`.

**Это меняет объём работы кардинально:**

1. **Есть отдельный namespace `api1c/RoboStorage/*`**, судя по всему созданный специально под эту программу: `GetStockTasks`, `GetStockTaskPositions`, `CreateStockTask`, `CreateStockTask2` (с телом для передачи кодов маркировки), `GetPositionsLog`, `GetPositionsStorageHonestSignCode(s)`, `GetPositionsStorageHonestSignCodesLogs`. Формат ответа `GetStockTaskPositions` практически 1:1 совпадает с полями таблицы `PositionsStorage`, которые мы вручную реконструировали по SQL-запросам (раздел 10) — то есть **этот API уже отдаёт ровно те данные, ради которых сейчас идёт прямой SQL-доступ к MS SQL Server**.
2. **Есть `POST api1c/Warehouse/PositionsSetStatuses`** — массовая смена статуса позиций с чистым JSON-ответом (`itsOk`, список `pst_id`/`pst_state_id`/`pst_state_id_new`). **Это прямая замена всей хрупкой HTML-эмуляции админки** (`Trade.cs`, `FormStock.PositionsSetStatus`, отдельная захардкоженная учётная запись для админки, раздел 11) — включая, скорее всего, замену того самого захардкоженного списка из 93 "разрешённых" статусов: если API сам валидирует переход, список на стороне клиента может быть вообще не нужен.
3. **Есть `GET api1c/Warehouse/GetOrderStates`** — это готовый эндпоинт для получения справочника статусов с человекочитаемыми названиями, ровно то, для чего в desktop-версии была брошена недописанная форма `FormStatusesSettings.cs` (раздел "MVP-скоп" выше).
4. **Есть полноценный раздел `Warehouse/shipments*` и `createshipment`/`createshipment2`** — отгрузка на стороне Stutzen — активно поддерживаемая часть API, что косвенно повышает вероятность, что вопрос "используется ли отгрузка" из раздела выше получит ответ "да" — но проверка через SQL остаётся самым быстрым способом получить точный ответ по конкретно вашему складу.

**Вывод: скорее всего, новая web-версия почти не будет напрямую обращаться к MS SQL Server/MySQL Stutzen — вместо этого она станет тонким клиентом `api1c`.** Это кардинально меняет архитектуру сервиса `stutzen-integration` (раздел "Архитектура" выше): вместо HTML-скрейпинга — обычный REST-клиент с retry/очередью, вместо ad-hoc SQL — типизированные DTO по документированным ответам API.

**Что нужно сделать дальше, прежде чем закладывать это в архитектуру:**
- Получить `ApiKey` и тестовый доступ к `api1c`, чтобы на практике проверить: действительно ли `PositionsSetStatuses` принимает переходы без ограничения по списку из 93 статусов, и что данные из `GetStockTaskPositions`/`GetPositionsStorageHonestSignCode(s)` покрывают 100% того, что сейчас берётся напрямую из `LocalDb`/`StutzenDb` (весь список полей `AppPosition`, раздел 11).
- Уточнить у Stutzen, насколько стабилен и поддерживается именно раздел `RoboStorage/*` — раз он назван под конкретное приложение, вероятно, изменения в нём будут согласовываться, в отличие от общего HTML-интерфейса админки.
- В документации не найдено формата тела запроса для нескольких методов (`PositionsSetStatuses`, `PositionEditStateID`) — только пример ответа; нужно запросить у Stutzen пример запроса или тестовый вызов через Postman/curl.

## 🟢 Поправка: официальный способ записи статуса найден

Файл `3.9.1` (создание/редактирование **позиции заказа клиента**, не заказа целиком) удалось получить отдельно — вывод из предыдущего раздела нужно скорректировать. `POST/PUT /api/v1/order-positions/` **официально принимает поле `statusID`** (плюс `statusExternalID`/`statusName`) — это задокументированный, поддерживаемый TradeSoft способ смены статуса, в отличие от `3.8.1` (заказ целиком), где такого поля нет.

Более того, у этого эндпоинта есть механизм именно под нашу задачу: поле **`subStates`** — массив, позволяющий одним запросом **разделить одну позицию на несколько с разными статусами** (документация приводит пример: "если в БД 5 позиций, subStates может быть 5, или 3+2, или 1+2+2, но не 2+2"). Это практически прямое соответствие логике из `FormStock.SavePosition` (раздел 11 основного документа), где одна ожидаемая позиция по факту распадается на "принято чисто / брак / недостача / пересорт" — тот самый случай, когда позицию нужно "расщепить" по нескольким исходам.

**Это меняет рекомендацию:** там, где раньше казалось, что придётся полагаться только на неофициальный `api1c/Warehouse/PositionsSetStatuses`, для **статуса позиции клиентского заказа** (который, судя по этикетке из раздела приёмки, и есть то, что реально меняется при приёмке — товар привязан к конкретному клиенту с самого начала) — есть официальный, документированный, поддерживаемый вендором путь: `api/v1/order-positions/`. Стоит на практике сравнить, какой из двух путей (`api/v1/order-positions` официальный vs `api1c/Warehouse/PositionsSetStatuses` неофициальный) реально использует текущая desktop-версия для конечного эффекта "статус заказа клиента изменился на сайте" — возможно, `api1c` можно вообще не переносить в новую систему, если `api/v1/order-positions` покрывает потребность полностью.



## 🟠 Уточнение по API TradeSoft/Stutzen — риски, которые важно понимать

Разобрал официальную документацию **TradeSoft REST API v1/v2** (общая платформа, на которой построен сайт Stutzen — не путать с `api1c`, разобранным выше). Три важных вывода:

1. **Другой механизм авторизации.** Здесь токен передаётся GET-параметром `?token=...` (а не заголовком `ApiKey`) и дополнительно может быть привязан к конкретным IP-адресам через админку сайта. `stutzen-integration` должен уметь работать с двумя разными схемами авторизации одновременно (v1 и `api1c`), и при деплое в Docker нужно будет зарегистрировать статичный исходящий IP контейнера в настройках токена на стороне Stutzen.
2. **Официальный API TradeSoft — read-only для того, что нам критично.** `API заказы поставщикам` (3.22) и `API позиции поставщика` (3.23) поддерживают **только `GET`**. `API заказы клиентов` (3.8) поддерживает создание/редактирование, но среди задокументированных полей **нет статуса заказа** — только отдельный `GET`-справочник состояний (4.14). Официальная документация прямо предупреждает: *"если для сущности не описан какой-то метод — его поведение не определено и может привести к падению проекта и потере данных"* — пробовать `POST`/`PUT` туда, где задокументирован только `GET`, вендор прямо запрещает.
3. **Вывод: вся используемая нами функциональность записи (смена статуса позиции, создание задания) — это `api1c/RoboStorage`/`api1c/Warehouse`, который, по вашему уточнению, написан не TradeSoft/Stutzen, а тем же разработчиком, что и сама RoboStorages.** Это меняет оценку риска по сравнению с первым впечатлением ("нашли готовый API, всё легко"): `api1c` — не официально поддерживаемая часть платформы TradeSoft, а частное расширение конкретного разработчика поверх неё. Он может быть таким же надёжным на практике, но **гарантий поддержки со стороны TradeSoft/Stutzen на него нет**. Стоит явно уточнить у собственника Stutzen: кто сейчас поддерживает и может дорабатывать `api1c`, и не стоит ли формализовать его статус (например, договориться, чтобы Stutzen официально взяли его на баланс как часть своей платформы) — прежде чем закладывать на него долгосрочную архитектурную зависимость.

**Практический вывод для архитектуры не меняется** (`stutzen-integration` как REST-клиент к `api1c`) — но стоит явно задокументировать в проекте, что это интеграция с полуофициальным, не гарантированным вендором API, и заложить в `stutzen-integration` слой абстракции (свой внутренний контракт), чтобы при необходимости можно было безболезненно переключиться на другой способ синхронизации статуса, если `api1c` перестанет поддерживаться.
## Технические детали TradeSoft REST API v1 (авторизация, формат, ошибки)

- **Авторизация:** GET-параметр `?token=...` в каждом запросе (не заголовок). Токен создаётся в админке сайта (`Настройки → Настройки REST API`), может быть привязан к конкретным IP — при деплое в Docker нужно зарегистрировать статичный исходящий IP интеграционного сервиса.
- **URL-паттерн:** `http://www.domain.ru/api/v1/{entity}/[{entityID}/]?token=...&filter=value`.
- **Методы:** `GET` (чтение, с фильтрами по полям сущности; выдача батчами по 1000 строк с `nextStartRow`/`startRow` для пагинации), `POST` (создание), `PUT`/`POST` с указанным ID (обновление), `DELETE` (удаление).
- **🔴 Опасность `DELETE` без фильтра:** если вызвать `DELETE` без GET-параметров фильтрации — удалятся **все** строки сущности (до 1000 за раз). Подтверждено явно для `order-positions` (`3.9.3`) и как общее правило (`1.4`). **В клиенте-обёртке `stutzen-integration` вызов DELETE без явного фильтра должен быть запрещён на уровне кода**, не полагаясь на дисциплину разработчиков.
- **🔴 Запрет на "угадывание" методов:** вендор прямо предупреждает — использование метода, не описанного для сущности (например, `POST` туда, где задокументирован только `GET`), может привести к падению системы и потере данных. Никаких "а вдруг сработает" в интеграционном коде.
- **Формат ответа:** всегда JSON `{ error, errorMessage, result }` — `error`/`errorMessage` заполняются при ошибке (например, `invalid_token`), `result` — либо ID созданной/обновлённой сущности, либо массив сущностей при чтении.
- **Особенность геопривязки:** сущности с адресом (клиенты, точки доставки) ищут соответствие в справочнике city/region/country — если город не найден во внутренней гео-базе TradeSoft, запрос вернёт ошибку. Не относится к приёмке напрямую, но важно для любых сервисов, работающих с адресами клиентов.
- **Пример на PHP** подтверждает стандартный REST: JSON-тело в `CURLOPT_POSTFIELDS` для POST/PUT/DELETE, никаких нестандартных заголовков — переносится на Python (`httpx`/`requests`) без сюрпризов.

### `api/v1/order-positions/` — официальный путь записи статуса позиции (важное дополнение к разделу выше)
`POST/PUT` принимает `positionID` + `statusID`/`statusExternalID`/`statusName`, а также **`subStates`** — массив для разделения одной позиции на несколько с разными статусами в одном запросе (ровно то, что нужно для сценария "часть партии принята чисто, часть — брак/недостача", раздел `SavePosition` основного документа). Это официальный, документированный TradeSoft путь — предпочтительнее неофициального `api1c/Warehouse/PositionsSetStatuses`, если оба реально приводят к одному и тому же результату на сайте (нужно проверить на практике).

## Итог по разделке скопа

Можно начинать проектирование архитектуры сервисов уже сейчас

**MVP = приёмка + маркировка + печать + права доступа + интеграция со Stutzen (статусы).**
**Вне MVP до уточнения = отгрузка, справочники, настройки статусов как UI.**

Если отгрузка окажется активно используемой — это отдельный, добавляемый позже сервис, не меняющий уже спроектированное ядро.
