### Про поля ответа `GetStockTasks`

- `deletet` — **1 означает «активная запись»**, а не «удалённая». Логика обратна названию. Все запросы десктоп-версии содержат `Deletet=1`, API удалённые не отдаёт. Поле бесполезно.
- `startTime`/`endTime` со значением `0001-01-01T00:00:00` — это .NET-способ записать «не заполнено», а не реальная дата.
- `rcp_id` дублирует `receiptNumber`.
- `stk_id` во всех записях `0`, назначение неясно. **Не путать с `id`.**

### Про базу RoboStorages (MS SQL)

| Факт | Как выяснено |
|---|---|
| Порт стандартный, 1433 | Диагностика, 02.09.2026 |
| Сервер принимает **только протокол TDS 7.0**. Версии 7.1–7.4 и умолчание рвут соединение с ошибкой `TDS server connection failed` | Диагностика, 02.09.2026 |

TDS 7.0 — протокол времён SQL Server 2000. Либо сервер старый, либо настроен консервативно. Для `pymssql` это задаётся параметром `tds_version="7.0"`; без него подключение не проходит, хотя десктоп-программа на .NET работает нормально (её драйвер договаривается иначе).

Практическое следствие: если понадобится подключаться к этой базе из Python (в том числе из сервиса `warehouse` на переходный период), про версию протокола нужно помнить. Скрипт `diagnose_mssql.py` подбирает рабочие параметры заново, если что-то изменится.

### Про поле «поставщик»

Строка `provider` формально имеет вид `ГОРОД-ГОРОД-НАЛОГ-Название (Бренд)`, но формат соблюдается не всегда. На реальных данных встречаются (03.09.2026, экран приёмки):

- почтовый адрес вместо названия организации: `г. <город>, ул. <улица>, д. <номер>`;
- адрес электронной почты внутри строки: `НСК-ОАЭ-ИП-<НАЗВАНИЕ> (КОНТЕЙНЕР) (<почта>)`;
- длинные строки, не помещающиеся в колонку.

Практическое следствие: разбирать эту строку на составляющие (город, юрлицо, бренд) регулярным выражением не выйдет — исключений слишком много. Либо показывать как есть, либо решать отдельно (см. отложенные идеи).

### Про связь задания и его позиций

**`GetStockTaskPositions` принимает `dcc_id`, и значение туда идёт из поля `documentNumber` задания.** Проверено пробником 02.09.2026: перебрано 7 имён параметров × 3 значения, сработало единственное сочетание.

Это неочевидно и легко перепутать:
- параметр называется `dcc_id`, хотя в ответе `GetStockTasks` поля с таким именем нет;
- поле `stk_id` в задании есть, но там всегда `0` — оно не подходит;
- поле `id` задания (например, 486715) тоже не подходит.

Подтверждается SQL-запросом десктоп-версии (`FormStock.cs`): `[PositionsStorage].[dcc_id] = [StockTasks].[DocumentNumber]`.

> Цена ошибки: при неверном параметре API отвечает `200 OK` и пустым списком — без всякой ошибки. Экран позиций просто окажется пустым, и причина будет неочевидна.

### Про десктоп-версию

- Отгрузка через RoboStorages **не используется** — подтверждено собственником Stutzen. Кладовщики только массово меняют статус на сайте, сам процесс идёт через сайт или 1С.
- Модули `Shipments.cs`, `UCShipment.cs`, `FormStatusesSettings.cs` — **пустые заготовки**, кнопки не подключены к обработчикам.
- `FormManager.CreateStockTask` — мёртвый код с захардкоженными тестовыми ID. Не использовать как образец.
- Меню в `FormLoginMenu` — это не разные модули, а один экран с разными парами статусов.
- Названия статусов задания хранятся в таблице `StockTasksStatus` (поле `StatusName`), через API недоступны.

## Принятые решения

| Решение | Причина |
|---|---|
| Локальное зеркало заданий в Postgres вместо прямых вызовов api1c | У api1c нет фильтров, постраничности и выборки по номеру; полная выгрузка 44 сек. Без зеркала экран кладовщика невозможен |
| Полная синхронизация редко (раз в сутки), инкрементальная часто | api1c отдаёт записи в порядке создания, а не изменения: смена статуса у старого задания в свежем срезе не всплывёт |
| Режим только чтения включён **по умолчанию** | Нет тестового контура, работаем против боевого Stutzen. Если переменная потеряется — система откажет в записи, а не испортит данные |
| Синхронизация статусов через очередь, а не прямым вызовом | Десктоп-версия теряла ошибки в пустом `catch{}` — сбой был невидим |
| Поиск позиции по скану — на сервере | Десктоп грузил всё задание в память и искал там; при большом приходе медленно |
| Только `stutzen-integration` ходит во внешние системы | Один слой абстракции: можно заменить механизм, не трогая остальные сервисы |
| Ключ «Честного Знака» только в сервисе `marking` | Юридически значимая система, ключ не должен попадать в браузер |
| MS SQL на переходный период, Postgres для нового | Пока десктоп и веб работают параллельно, нужна общая база |

## Грабли, на которые уже наступили

Ошибки, которые уже случились в этом проекте. Каждая закреплена тестом.

**Статус 3 считали активным.** Фильтр «статус != 4» тащил бы в список кладовщика 8654 архивных задания, включая записи 2017 года. Правильно: активные — 1, 2, 5, 6; завершённые — 3, 4. Тест `test_status_3_is_treated_as_finished`.

**`ILIKE` не приводит регистр кириллицы в SQLite.** Тесты идут на SQLite, прод на PostgreSQL. В PostgreSQL поиск по поставщику работал бы верно, в SQLite — нет: встроенное приведение регистра там обрабатывает только латиницу. Код вёл бы себя в тестах и в проде по-разному.
Решение: отдельное поле `provider_search`, заполняемое через `str.lower()` в Python при записи — результат одинаков в любой базе. Тест `test_filter_by_provider_is_case_insensitive_for_cyrillic`.
Общий вывод: **тестовая база отличается от боевой**. Держать в голове при любой работе со строками, сортировками и датами.

**Неверный параметр в `GetStockTaskPositions` не даёт ошибки.** API отвечает `200 OK` и пустым списком. Экран просто окажется пустым, причина не видна. Поэтому параметр метода в клиенте назван `document_number`, а не `task_id` — чтобы нельзя было передать id задания по невнимательности.

**Переменные окружения от пробников утекали в тесты.** Пробники запускаются так: в окне PowerShell вручную задаётся `API1C_BASE_URL` и `API1C_API_KEY`, и живут они до закрытия окна. В `conftest.py` тестовые значения задавались через `setdefault` — то есть уступали уже заданным. В результате тесты оказались настроены на **боевой Stutzen с настоящим ключом**.
Решение: в `conftest.py` всё, что может увести в боевые системы (адреса, ключи, база, очередь), присваивается безусловно, а не через `setdefault`. Тест `test_test_env_does_not_point_at_production` проверяет это и ловит возврат к прежнему поведению.
Общий вывод: **тестовое окружение не должно зависеть от того, что осталось в терминале.**

**Обязательные поля в модели зеркала = потеря данных. Дважды.**

Зеркало копирует чужую систему с данными с 2017 года, качеством которых мы не управляем. Каждое поле, объявленное обязательным, означает: запись с пустым значением не разберётся и **молча исчезнет**.

- Сначала обязательным был `stock_id` — потерялись 5 активных заданий.
- Потом обязательным оставался `login` — потерялись **65 700 записей, 14,5% всей базы**. Полная синхронизация положила в зеркало 387 585 записей вместо 453 295, и это осталось незамеченным, пока не начали считать пропуски.

Оба раза чинили одно поле и не проверяли остальные.

Решение:
1. Обязательным остался только `id` — ключ записи. Всё остальное принимается как пришло. Проверять полноту — задача экрана: лучше показать приход без автора, чем не показать приход.
2. Разбор считает пропуски и называет причины (`ParseResult.report()`), синхронизация пишет это в лог с уровнем ошибки.
3. Тест `test_every_field_except_id_may_be_empty` проверяет **все поля разом**, а не одно — чтобы третьего раза не было.

Общий вывод: **молчаливый `except: continue` скрывает не мусор в данных, а наши неверные допущения о них.** Если пропуски не считаются, потеря 14% базы выглядит как нормальная работа.

**Полная синхронизация обрывалась по таймауту.** В клиенте api1c стоял общий таймаут 10 секунд, а полная выгрузка идёт около 40 (186 МБ). Инкрементальная синхронизация при этом работала нормально — она укладывалась в лимит. То есть сломан был только тяжёлый режим, и заметить это можно было, лишь запустив именно его.
Решение: разные таймауты для разных запросов (`timeout_for` в `api1c_client.py`), решение вынесено в отдельную функцию, чтобы его можно было проверить тестом. Файл `tests/test_api1c_timeouts.py`.
Общий вывод: **режим, который запускается редко, ломается незаметно.** Пробники это скрывали — им таймаут задавался вручную.

## Отложено до появления работающей приёмки

Идеи, которые обсуждали, но решили не делать сейчас. Вернуться, когда ядро заработает и появится статистика по реальной работе кладовщиков.

**Применение ИИ внутри приложения** (обсуждалось 02.09.2026).

Не подходит для расчётов количества, статусов и сверки маркировки — там нужна предсказуемость, а ошибка стоит денег. Обычный код надёжнее, быстрее и дешевле.

Где может дать пользу:
- Разбор строки поставщика — сейчас это `«МСК-МСК-НДС-ООО НАЗВАНИЕ (БРЕНД)»`, где город, налоговый режим, юрлицо и бренд слеплены вместе. Оговорка: сначала проверить, не хватит ли обычного регулярного выражения — зависит от того, насколько формат стабилен.
- Подсказки при расхождениях: привезли не тот артикул — показать похожие позиции из этого же задания. Решение остаётся за кладовщиком.
- Поиск по свободному тексту вместо заполнения нескольких фильтров.

Причина отложить: работает один эндпоинт из десятка, ядро приёмки не написано. Добавлять ИИ в приложение, которое пока не делает основную работу, — способ получить и то, и другое наполовину. Возвращаться, когда будет видно, где кладовщики реально тормозят.

## Известные ограничения

Осознанные компромиссы, а не недоработки. Важно, чтобы про них знали.

- **Зеркало отстаёт от Stutzen.** Если задание закроют в десктопной программе, наш список какое-то время покажет его открытым. Страховка: при открытии конкретного задания данные запрашиваются напрямую.
- **Работа идёт на боевых данных.** Тестового контура нет и не будет — ограничение со стороны Stutzen. Защита: режим только чтения по умолчанию.
- **Один ключ API на всех.** Разделить окружения по ключам невозможно.
- **Секреты десктоп-версии скомпрометированы.** Пароли обеих баз, ключ API и служебная учётная запись лежали открытым текстом внутри программы, установленной на компьютерах склада. Пока они не сменены, репозиторий должен оставаться приватным.
