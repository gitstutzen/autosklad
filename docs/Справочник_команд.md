## Git: первый запуск проекта

### Настройка git (один раз на компьютер)
```powershell
git config --global user.name "Ваше Имя"
git config --global user.email "ваша@почта.ru"
```
Почту указывайте ту же, что на GitHub — тогда коммиты привяжутся к аккаунту.

### Клонировать существующий репозиторий
```powershell
git clone https://github.com/gitstutzen/autosklad.git
cd autosklad
```

### Создать репозиторий с нуля (если начинаете с локальной папки)
```powershell
git init
git branch -M main
git add .
git status                    # ← ОБЯЗАТЕЛЬНО посмотреть глазами
git commit -m "Начальная структура проекта"
git remote add origin https://github.com/gitstutzen/autosklad.git
git push -u origin main
```

### Проверить, к какому репозиторию подключена папка
```powershell
git remote -v
```

## Git: повседневная работа

### Стандартный цикл работы над задачей
```powershell
git switch main               # перейти на основную ветку
git pull                      # забрать свежие изменения

git switch -c feat/название   # создать ветку под задачу и перейти в неё
# ... работаете ...
git add .
git status                    # проверить, что добавляется
git commit -m "warehouse: краткое описание"
git push -u origin feat/название   # первый пуш ветки
```

Дальше на GitHub появится кнопка **Compare & pull request** — создаёте PR, коллега ревьюит, вливаете.

### Последующие пуши в ту же ветку
```powershell
git add .
git commit -m "warehouse: ещё одно изменение"
git push                      # уже без -u
```

### Именование веток
```
feat/       новая функциональность      feat/scan-position-endpoint
fix/        исправление бага            fix/status-calculation-overflow
docs/       только документация         docs/update-api-reference
refactor/   рефакторинг без новых фич   refactor/extract-db-layer
chore/      рутина (зависимости, CI)    chore/bump-fastapi
```

### Именование коммитов
Префикс сервиса + повелительное наклонение:
```
warehouse: добавлен расчёт статуса при частичной приёмке
auth: исправлена проверка срока действия токена
docs: обновлён справочник API Stutzen
```

### Посмотреть, что происходит
```powershell
git status                    # что изменено сейчас
git status --short            # то же, компактно
git diff                      # что изменилось, но не добавлено в коммит
git diff --staged             # что добавлено, но не закоммичено
git log --oneline -10         # последние 10 коммитов
git branch                    # список локальных веток
```

### Добавление файлов выборочно
```powershell
git add .                              # всё
git add services/warehouse/            # только один сервис
git add services/warehouse/app/main.py # конкретный файл
```

### Отменить изменения
```powershell
git restore <файл>            # откатить правки в файле (до последнего коммита)
git restore --staged <файл>   # убрать файл из добавленных (правки останутся)
git switch -                  # вернуться на предыдущую ветку
```

## Git: решение проблем

### Конфликт при слиянии (`CONFLICT (add/add)`)
Возникает, когда один и тот же файл изменён и локально, и на сервере.

Оставить **нашу** версию файла:
```powershell
git checkout --ours README.md
git add README.md
```

Оставить версию **с сервера**:
```powershell
git checkout --theirs README.md
git add README.md
```

Затем завершить слияние:
```powershell
git status                    # убедиться, что нет "Unmerged paths"
git commit -m "Слияние с начальным README репозитория"
```

### Ошибка `Updates were rejected... remote contains work that you do not have`
На сервере есть коммиты, которых нет локально (обычно — README, созданный при инициализации репозитория на GitHub).
```powershell
git pull origin main --allow-unrelated-histories
# разрешить конфликты, если появятся (см. выше)
git push -u origin main
```

### Удалить файл из репозитория
```powershell
git rm "имя файла.md"                    # удалить и из папки, и из git
git rm --cached "имя файла.md"           # убрать из git, оставить на диске
git commit -m "docs: удалены дубликаты"
```
> В PowerShell для имён с кириллицей: наберите начало имени и нажмите **Tab** — имя подставится автоматически.

### Посмотреть версию файла на сервере, не скачивая её
```powershell
git show origin/main:README.md
```

### Если в редакторе Vim открылось окно ввода сообщения
Нажмите `:wq` затем Enter — сохранить и выйти.
Если нужно отменить: `:q!` затем Enter.

## Docker

Все команды выполняются **из папки `infra`**:
```powershell
cd infra
```

### Запуск и остановка
```powershell
docker compose up --build     # собрать и запустить всё (первый запуск — несколько минут)
docker compose up -d          # запустить в фоне
docker compose down           # остановить
docker compose down -v        # остановить + УДАЛИТЬ данные БД (полный сброс)
docker compose restart warehouse   # перезапустить один сервис
```

### Подготовка окружения (перед первым запуском)
```powershell
copy .env.example .env        # Linux/macOS: cp .env.example .env
```
Затем откройте `.env` и заполните значения — как минимум `JWT_SECRET`.

### Диагностика
```powershell
docker compose ps                    # что сейчас запущено
docker compose logs -f warehouse     # логи одного сервиса, в реальном времени (Ctrl+C — выход)
docker compose logs --tail=50        # последние 50 строк всех логов
docker compose logs warehouse        # все логи одного сервиса
docker compose exec warehouse bash   # зайти внутрь контейнера
```

### Пересборка
```powershell
docker compose build warehouse       # пересобрать один сервис
docker compose up --build            # пересобрать и запустить всё
```

### Типовые проблемы

**`port is already allocated`** — порт занят другой программой.
Частый случай: локально установленный PostgreSQL занимает `5432`. В проекте Postgres специально проброшен на `5433`. Если конфликтует что-то другое — поменяйте левое число в секции `ports` в `infra/docker-compose.yml`.

**Изменения в коде не подхватились** — Docker использует старый образ.
```powershell
docker compose up --build
```

**Осталась старая конфигурация после правки docker-compose.yml**
```powershell
docker compose down -v
docker compose up --build
```

## Тесты

Выполняются из папки конкретного сервиса.

### Подготовка окружения (один раз на сервис)
```powershell
cd services\warehouse
python -m venv .venv
.venv\Scripts\activate               # Linux/macOS: source .venv/bin/activate
pip install poetry
poetry install
```

### Запуск
```powershell
pytest                               # все тесты сервиса
pytest -v                            # с именами тестов
pytest -x                            # остановиться на первой ошибке
pytest tests\test_determine_status.py                    # один файл
pytest tests\test_determine_status.py::test_excess       # один тест
pytest -k "status"                   # все тесты, где в имени есть "status"
```

### Выход из виртуального окружения
```powershell
deactivate
```

## Зависимости Python

У каждого сервиса свой `pyproject.toml` — зависимости не общие.

```powershell
cd services\warehouse
poetry add httpx                     # добавить обычную зависимость
poetry add --group dev pytest-cov    # добавить dev-зависимость
poetry remove httpx                  # удалить
poetry lock                          # пересобрать lock-файл
poetry show                          # список установленного
```

После добавления зависимости пересоберите контейнер:
```powershell
cd ..\..\infra
docker compose build warehouse
```

## Проверка перед коммитом

Выполнять **каждый раз** перед `git commit`:

```powershell
git status                                    # посмотреть глазами весь список
git status --short | Select-String "\.env$"   # проверка, что .env не попал
```

Если вторая команда ничего не вывела — хорошо. Если вывела `infra/.env` — **не коммитьте**, разберитесь, почему `.gitignore` не сработал.

### Что нельзя коммитить никогда
- `.env` и любые файлы с реальными паролями, ключами, токенами
- Сами значения секретов в комментариях и документации (описывать проблему — можно, приводить пароль — нет)
- Закомментированный код «на всякий случай» — для этого есть история git

> **Если секрет всё-таки попал в коммит** — обычным коммитом это не исправляется, значение остаётся в истории. Сообщите команде: секрет считается скомпрометированным и подлежит ротации.

## Адреса сервисов

После `docker compose up`:

| Сервис | Адрес | Документация API |
|---|---|---|
| gateway | http://localhost:8000 | http://localhost:8000/docs |
| auth | http://localhost:8001 | http://localhost:8001/docs |
| warehouse | http://localhost:8002 | http://localhost:8002/docs |
| marking | http://localhost:8003 | http://localhost:8003/docs |
| print | http://localhost:8004 | http://localhost:8004/docs |
| stutzen-integration | http://localhost:8005 | http://localhost:8005/docs |
| PostgreSQL | localhost:**5433** | — |

Проверка, что сервис жив: откройте `/health` — должно вернуться `{"status":"ok"}`.

> **Напоминание:** часть эндпоинтов сейчас намеренно возвращает ошибку 500/501 — это заглушки, а не баги. Полностью работают расчёт статуса приёмки и защитные правила клиента к API Stutzen (оба покрыты тестами).
