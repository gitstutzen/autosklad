# Итоги первого этапа

Срез состояния на 3 сентября 2026 года, работа приостановлена. Документ отвечает на три вопроса: что сделано, что осталось, с чего продолжать.

---

## Что сделано

### Разобрались, что делает старая программа

RoboStorages оказалась не самостоятельной системой, а **прослойкой между физическим складом и сайтом Stutzen**. Кладовщик сканирует пришедший товар, программа сверяет с накладной, печатает этикетку, проверяет маркировку и сообщает сайту, что товар доехал.

Отдельно выяснилось, что переносить нужно меньше, чем казалось:

- **отгрузка не используется** — подтверждено собственником Stutzen;
- несколько экранов оказались недописанными заготовками: кнопки не подключены к обработчикам;
- десяток пунктов меню — это один и тот же экран с разными фильтрами, а не разные модули.

Подробности — в `RoboStorages_приёмка_как_это_работает.md` и `RoboStorages_scope_MVP.md`.

### Изучили API Stutzen на практике

Документации по нужным методам не было — всё выяснено пробниками на боевом API. Главное:

| Что | Выяснено |
|---|---|
| Фильтры в списке заданий | Не работают, кроме `count` |
| Постраничность | Отсутствует |
| Выборка по номеру задания | Отсутствует |
| Позиции задания | Запрашиваются по `dcc_id` = `documentNumber` задания |
| Полная выгрузка | 453 000 записей, 186 МБ, около 44 секунд |
| Названия статусов | В API отсутствуют, прочитаны напрямую из базы |

Ни один из этих фактов не следует из документации Stutzen. Все они записаны в `Записная_книжка_проекта.md` с указанием, как проверялись.

### Написали работающий слой чтения

Сервис `stutzen-integration` умеет:

- забирать задания из Stutzen — полностью и по свежему срезу;
- хранить их в локальном зеркале с фильтрами, которых нет в API;
- отдавать позиции внутри задания;
- переводить числовые статусы в понятные названия.

**70 тестов**, все проходят. Проверено на боевых данных: полная синхронизация обрабатывает 453 305 записей за 192 секунды, занимает 121 МБ памяти.

### Собрали экран для показа людям

Список приходов слева, позиции внутри выбранного прихода справа. Работает на реальных данных, изменить ничего нельзя. Готов к тому, чтобы показать кладовщикам и собрать замечания.

### Заложили защиту от главного риска

У проекта нет тестового контура: разработка и продакшн работают против одного боевого API Stutzen с одним ключом. Отсюда:

- **режим только чтения включён по умолчанию** — и остаётся включённым, если переменная потеряется или будет опечатана;
- все обращения наружу журналируются, ключи в логи не попадают;
- `DELETE` без фильтров запрещён программно (в API Stutzen он удаляет всю сущность);
- вызов недокументированных методов запрещён — прямое предупреждение вендора о риске потери данных;
- тесты не могут случайно уйти в боевую систему: проверяется отдельным тестом.

## Чему научились на ошибках

Пять ошибок, каждая закреплена тестом. Подробности — в разделе «Грабли» записной книжки.

**Статус 3 считали активным.** Фильтр «всё, кроме статуса 4» тянул бы в список кладовщика 8 600 архивных заданий, включая записи 2017 года.

**Обязательные поля в модели зеркала = потеря данных.** Дважды: сначала потеряли 5 заданий из-за поля «склад», потом 65 700 записей — 14,5% всей базы — из-за поля «автор». Оба раза чинили одно поле и не проверяли остальные. Теперь обязательным остался только идентификатор, а тест проверяет все поля разом.

**Молчаливый пропуск битых строк скрывает не мусор, а наши неверные допущения.** Потеря 14% базы выглядела как нормальная работа, пока не начали считать пропуски.

**Тестовая база отличается от боевой.** Поиск по поставщику работал бы в продакшне и не работал в тестах: SQLite не приводит регистр кириллицы.

**Режим, который запускается редко, ломается незаметно.** Полная синхронизация была сломана таймаутом с самого начала — при этом ежеминутная работала нормально.

## Что не сделано

Ничего из перечисленного не начато — это честный список, а не «почти готово».

**Приёмка.** Ядро системы: принять количество, отметить брак или недостачу, отсканировать маркировку. Требует записи в боевой Stutzen, то есть выхода из безопасного режима только чтения.

**Печать этикеток.** Логика рендера в старой программе спроектирована хорошо и переносится почти без изменений, но печать на термопринтер из браузера требует отдельного небольшого агента на складе.

**Вход и права.** Есть проверка токена, но самой выдачи токенов нет. Модель прав в старой программе (текстовые списки логинов) переносить не стоит — нужна нормальная.

**Остальные сервисы** — маркировка, печать, единая точка входа — существуют как заготовки с честными пометками «здесь пока ничего нет».

## Открытые вопросы

Полный список — в записной книжке. Четыре самых важных:

1. **Как называются склады.** Номера в заданиях не совпадают со справочником складов: у склада 2 больше всего приходов, но такого номера в справочнике нет. Пока экран показывает «Склад 2» вместо названия города.
2. **Почему приход остаётся активным, когда все позиции приняты.** Замечено на экране: обе позиции приняты, задание открыто. Кто и когда его закрывает?
3. **Кто поддерживает `api1c`.** Это не официальная часть платформы TradeSoft, а расширение, написанное разработчиком старой программы. Гарантий на него нет.
4. **Секреты старой программы скомпрометированы.** Пароли обеих баз, ключ API и служебная учётная запись лежали открытым текстом внутри программы, установленной на складских компьютерах. Пока они не сменены, репозиторий должен оставаться приватным.

## С чего продолжать

Порядок предлагается такой, и он не случаен: сначала то, что уточняет требования, потом то, что требует риска.

**Первое — показать экран кладовщикам.** Он готов. Обратная связь от людей сейчас даст больше, чем любая следующая техническая деталь: проявятся вопросы, которых из кода не видно. Заодно закроются вопросы 1 и 2 из списка выше.

**Второе — приёмка.** Только после того, как процесс подтверждён людьми. Начинать стоит с приёмки без записи наружу: сохранять результат у себя, сверять с тем, что делает старая программа на тех же данных. Выходить из режима только чтения — последним шагом, когда всё остальное сверено.

**Третье — параллельный запуск.** Кладовщик работает в старой программе, новая молча пишет то же самое, результаты сравниваются. Расхождение — это найденная ошибка, найденная до того, как она испортила учёт.
